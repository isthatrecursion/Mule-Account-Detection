# Performance experiment protocol

Version: `benchmarks_v1`. [Benchmark configuration](../config/benchmarks.yaml) defines expected limits, not results. All `observed` values remain null. The CPU allocation, 16 GiB RAM, five clients, five repetitions, 12 GiB capacity memory ceiling, epsilon and workload sizes are proposed research experiment settings; they are not measured hardware or organization-approved service levels. Architecture targets remain 10,000 rows in **under 900 seconds**, read p95 **under 500 ms**, and 100,000-row capacity without redesign. Production targets require owner review.

## Repeatable input and setup

For each scenario merge `reference_hardware`, `common` and scenario fields; record the fully resolved configuration and hash. P12 supplies the generator/harness; this phase specifies it rather than claiming that a benchmark executable exists. A run is NOT_RUN until that harness and a frozen synthetic model bundle exist.

The synthetic generator contract `synthetic_benchmark_v1` uses one NumPy PCG64 generator with seed 20261020 and a pinned NumPy version. Generate unique synthetic account keys in numeric order and 3,924 input columns (`S1`–`S3924`). Iterate columns in ascending numeric order, generating a vector in account order, then that column's independent missingness mask from the same generator (`uniform < 0.05`). Assign families by zero-based column index modulo 10: 0–7 float64 standard normal, 8 float64 lognormal(0,1), 9 categorical sampled from `[SYN_A,SYN_B,SYN_C,SYN_D]` with equal probability. Thus approximately 80% are normal, 10% lognormal and 10% categorical. The synthetic frozen candidate contract selects `S1`–`S2521`; it does not reproduce historical exclusion semantics. No labels enter the scoring matrix. Pin schema, dependency lock and frozen synthetic pipeline/model bundle in the run manifest. No historical private rows are read, copied or repeated. Record exact input bytes, candidate feature list and eligible-row count; all accounts are eligible in these scenarios.

Use 10,000/100,000 rows as configured, top K=50 and one worker/two model threads. Batch timing starts after accepted input is durable, ends after scores, top-K explanations and queue publication commit. Record validation/intake separately so batch timing is not mistaken for end-to-end source arrival latency. Capacity success requires exact row accounting, zero lost/duplicate results, no OOM and measured peak RSS within the proposed memory envelope. Capacity latency is reported; no 15-minute requirement is invented for 100,000 rows.

Record actual CPU model/allocation, RAM, OS, SSD/filesystem, worker/thread limits, image digest, dependency versions, input/bundle/config digests and code revision before any measured result is valid. A substituted hardware profile must have a distinct ID; never silently compare profiles. Unknown CPU model and payload bytes in the design must be replaced by measured values in execution manifests.

## Measurement procedure

Run five measured repetitions per cache state. Cold means fresh worker/API process with unloaded bundle and fresh application/database session caches; OS disk caches are not assumed flushed and their state must be recorded. Warm means one excluded warmup run with loaded bundle/DB caches, then measured runs. Keep the input/model hashes fixed. Record wall-clock duration using a monotonic clock and UTC start/end times for provenance. Save all samples, failures, peak RSS, CPU time and raw per-request durations; do not drop failing repetitions. Summarize p50/p95/max with sample counts. Calculate p95 by nearest rank `ceil(0.95*n)` in the sorted durations. Batch limit applies to every measured repetition.

API reads use five clients, each issuing 200 requests to each endpoint (queue page size 50, case detail with pinned evidence payload); requests within a client are sequential, clients concurrent. Choose case IDs cyclically from the first 50 synthetic queue keys, no think time. Record complete response bytes and p95 separately by endpoint and cache state, including serialization/network time. Do not hide errors in latency summaries; failure budget is zero. The same request schedule runs during reconciliation.

## Delay experiment

Use 100,000 synthetic events over 10,000 accounts, ten per account, one required source with two partitions (`account_index mod 2`), independent monotonically increasing partition sequence numbers. Event time is synthetic UTC `2026-01-01T00:00:00Z + event_round*60s + account_index*1ms`, ordered by `(event_time,event_id)`. Each event has unique ID, amount `1 + account_index mod 1000`, currency `TEST`, alternating direction by event round, synthetic event type and schema. Freeze an approved synthetic feature contract and bundle; never convert this ledger into anonymous historical F features. Emit count/sequence completeness manifests every simulated minute. Select every fifth account as affected (2,000), delay its event rounds 2 and 7 by exactly 600 seconds. Additional versioned replay scenarios must cover high-value/high-risk, partition/window boundaries, duplicates, reversals, outage with unknown scope and beyond-grace arrival.

Replay identical contents twice (timely and delayed) with fixed virtual event schedule, hardware, model, feature contract and policy. Drive scan at most every 60 seconds plus arrival-triggered reconciliation. Compute timing excludes intentional delay and queue waiting; report those separately. `assessment_consistency` uses the same eligible accounts in both runs, identical frozen band and absolute raw-score difference ≤ configured epsilon. Top-K overlap is `|timely_topK ∩ delayed_topK| / K` for this fixture (K=50); a smaller eligible cohort uses its actual selected count; empty comparisons are NOT_APPLICABLE, never automatic passes. Overhead is `(delayed_p95-reference_p95)/reference_p95` for affected and unaffected accounts separately; zero reference duration or empty samples invalidates that metric. Freshness lag includes upstream delay and is `published_at-event_time` for delayed events. Save per-account samples and corrected event/feature/model lineage.

All configured replay limits must pass, including ≥95% assessment consistency/queue overlap, ≤5% affected compute overhead/unaffected regression, zero loss/duplicates/downgrades, 100% lineage and p95 freshness ≤660 seconds. Synthetic event agreement proves engineering behavior only. Real predictive evidence requires representative timestamped source data and mature outcomes, with AP, ROC-AUC, P@K/R@K, score deltas and rank displacement. No performance claim exists until run evidence is reviewed.
